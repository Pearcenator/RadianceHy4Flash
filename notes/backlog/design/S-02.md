# S-02 design: the layer-sliced prefill chunk

Design card of [S-02](../optimisation-backlog.md#s-02-layer-sliced-prefill-chunk-decoders-ride-a-slice-of-the-chunks-layers)
(`#19`), after S-01 (merged as config only: `--checkpoint-interval 1984`, so no chunk takes a remainder step) and M-03
(the stager arms only above its top level, 1025 rows at 2048, which is the floor §2.3's row minimum sits beside).
Lane: none — this note is written and checked without a card.
It plans two build cards, S-02a (scheduler, ABI, stager plumbing; no gain on its own) and S-02b (the plugin's
sliced step and the measurement). §12 holds the two bodies.

S-02a merged (`eeaf5e97`). S-02b was built, run on the lane and reverted, and the item is closed without code:
[closed/S-02-exec.md](../closed/S-02-exec.md) holds the numbers and the reason. Read it before re-landing anything
below: a sliced prefill chunk is byte-identical to an unsliced one (§8.2's check, done), and what the lane refused is
the time, so a re-land starts from §5's stager fallbacks and not from this plan's step 1.

The item says: plan a chunk as m sub-steps; sub-step j runs the decode rows through all 42 layers and the chunk rows
through layers `[L_j, L_{j+1})`; the trunk's per-token state for the chunk's rows persists between sub-steps; the
stager stages per slice. This note fixes what each of those means at HEAD `35c03cb6`, what it costs, and what the two
build cards must show.

Everything below is a plan, not a measurement. The numbers in §2.7 and §10 are predictions to falsify on a lane; they
come from the measured chunk and decode step times of this tree (§1), and the model that turns them into a sub-step is
stated so a lane run can refute it in one pass.

## 0. The decisions, one by one

- **D1** A sub-step is an ordinary scheduler step carrying a mixed batch: the decode set's rows through all 42 layers,
  the chunk's rows through the slice's layers. Nothing else about a step changes (arena level, plan shape, counters).
- **D2** The slice boundaries are `L_j = floor(j·42/m)`, computed by the scheduler and carried to the plugin in two new
  `RadBatch` fields, `layer_lo`/`layer_hi` (`layer_hi == 0` = the whole trunk, so every caller that does not set them
  gets today's pass).
- **D3** The decode set is frozen for the whole chunk group (`m` sub-steps), because the chunk's rows sit at
  `[n_tok_decode, T)` and that base must not move. No admission, no preemption, no finish, no draft-depth change inside
  a group. And a group is only formed when the set is **one row a sequence** (`n_spec == 0`): hy4-flash's draft passes
  (the query pass and the block pass) are steps of their own (`scheduler.cpp:3960`, `:4202`), so a group whose decoders
  rode verify rows would have no scheduled step to draft for them. That costs nothing by default — this arch's `auto`
  keeps speculation off (`hyv4flash.cpp:1351-1355`: the draft pass's cost against a verify row is not measured) — and a
  deployment that asks for a depth gets m = 1 until the draft passes become steps of a group (a follow-up, §12).
- **D4** The chunk group is a small state machine in the scheduler: the entry is planned once, its `n_tokens` is held in
  the request's `sched_tokens` until the last sub-step, and `r.n_computed`, the KV window trim, the sink progress, the
  prefix publish, the checkpoint stage and `produces_token` all wait for the last sub-step ("commit deferral").
- **D5** The chunk's persistent trunk state is `RAD_BUF_PERSIST` for `tr.h`, `tr.xn`, `tr.post` and the boundary
  junction's int8 code pair (two buffers) when slicing is compiled in and enabled — **66 MiB a rank at
  `max-num-batched-tokens: 2048`** (69.4 MB), not the item's 50 MiB (which is `tr.h` alone). Every other trunk buffer
  stays transient.
- **D6** A sliced pass is never recorded: `Ctx::pass_key` returns 0 when `layer_hi != 0`, beside the plugin's existing
  "mixed and prefill passes are unrecorded". The ABI bumps 43 → 44 for the two fields and the capability flag.
- **D7** The stager stages per slice as it already stages per layer of the pass, with one change: the early staging of
  the *next* pass must be told the next pass's first layer (`set_next_prefill(bool more, int32_t first_layer)`), or it
  stages layer 0 for a pass that starts at `L_{j+1}`. The level never changes inside a group (same `n_tok`), so its ring
  needs no rebase.
- **D8** A chunk carrying a checkpoint is still sliceable at this HEAD: `plan_chunk` cuts a chunk *at* the checkpoint, so
  the snapshot is at the chunk's tail and the last sub-step is the chunk's end. The general guard (a snapshot strictly
  inside a chunk ⇒ m = 1) is kept for a plugin with an in-step snapshot, which hy4-flash is not.
- **D9** Byte-identical continuation is claimed for **the chunk's rows**: the same KV bytes, the same `final_hidden` row,
  the same logits and the same text as the unsliced chunk. It is *not* claimed for a decoder's token inside a mixed step:
  its non-slice layers run with `M = n_tok_decode` instead of `M = n_tok`, and this tree already states that the trunk's
  GEMMs are batch-dependent (`docs/ARCHITECTURES.md:3863`, `notes/wp13-7`, not in this tree). The item's Verify row must
  say so, or it will be read as a stronger promise than any engine here can keep.
- **D10** Slicing is off by default in S-02a (`--chunk-slices off`), proposes `auto` in S-02b, and does not touch
  `prefill-interleave`: the two are orthogonal (a sub-step *adds* cheap decoder tokens; the interleave *buys* decoder
  time with arrival time). §10 measures both pairs, because that is the only way to show TTFT is not worse.
- **D11** A sliced pass never takes the pipeline (`layer_lo > 0 || layer_hi < n_layer` ⇒ serial), never runs with the
  debug taps on, and never runs a calibration program — the out-of-slice row band would leave the taps of the layers
  outside the slice stale and the taps' cost model is built on whole-trunk passes. The plugin says
  `RadArchProbe::slice_layers_ok = 0` in those cases and the scheduler then plans m = 1.
- **D12** A cancel, an EOS or a KV shortfall during a group waits for the group's last sub-step. The rows keep being
  issued (the base is frozen) and the commit drops them as it already drops a row whose request left `Running`.

## 1. What the stall is at HEAD

The arrival stall is one chunk step. From the TP2 sweep in `docs/ARCHITECTURES.md:3774-3785` (`work/sweep` at
BetterBench `--workload`, 2 and 4 background streams, 16K arrivals, `max-num-batched-tokens: 2048`; the first table of
that section):

| setting | worst stall 2 / 4 streams | stall p99 | bg tok/s a stream in the window | 16K arrival TTFT p50 |
|---|---|---|---|---|
| `auto` (default: `busy-prefill-chunk: auto`, `prefill-interleave: auto:1`) | 762 / 812 ms | 713 / 715 ms | 33.4 / 24.4 | 9.5 / 10.3 s |
| `busy-prefill-chunk: 512` | 445-455 / 503-513 ms | 369-374 / 418-422 ms | 37.0-44.0 / 26.3-26.7 | 15.4-16.1 / 16.7-16.9 s |
| `busy-prefill-chunk: 256` | 384 / 444 ms | 270 / 348 ms | 44.9 / 28.0 | 21.6 / 24.6 s |
| `prefill-interleave: 0` | 712 / 710 ms | 712 / 710 ms | 7.7 / 7.4 | 5.0 / 5.5 s |

Cold prefill in that sweep is 3.96K tok/s at a 2K prompt, 3.50K at 16K and 2.96K at 64K; a 2048-row chunk is **565 ms
of op time** (34 % attention, 32 % routed MoE, 14.5 % trunk GEMMs, 11 % the two-rank junction;
`optimisation-backlog.md:20-27`, `:553`). The decode step is **13.5-13.8 ms** at one stream and **4.1 ms** for a draft
pass (`optimisation-backlog.md:20-27`); in the arrival windows the decoders' measured step is 12.9-13.0 ms at two
streams and 18.2-18.5 ms at four (`docs/ARCHITECTURES.md:3836`).

The in-tree re-run of the same frontier — `scripts/backlog/probe.py`'s `stall1,stall4` at `RADIANCE_LOG_STEPS=1` on
`local`/TP2/`nospec.yaml`, a 5.7K arrival behind 1 and 4 decoders, which is what §10 can reproduce — gives `auto`
**2.40-2.85 / 2.42-2.48 s** of arrival TTFT, worst stall **0.60-0.78 / 0.58-0.60 s**, three chunks of 1728-1984 rows
and 0.42-0.50 ms a prefill token (`docs/ARCHITECTURES.md:3815-3817`). Those are the numbers arm A of §10 must land in,
and the ones a slice must divide.

Two facts decide the whole design:

1. The stall is the chunk step, and shrinking the chunk buys stall only by paying rate: `busy-prefill-chunk: 256`
   takes the stall from 762 / 812 ms to 384 / 444 ms and the 16K arrival from 9.5 / 10.3 s to 21.6 / 24.6 s in the
   first window; in the in-tree one 512 rows is 12 chunks of 192-512 rows, 0.92-1.02 ms a prefill token and 4.83-5.83 s
   of arrival against 2.40-2.85 s (`:3819`). A 256-row chunk still reads every expert of every layer, so that
   direction's floor is the expert read, not zero. M-13's clamp (the learned cap at `mixed-step-target-ms: 150`, the
   "after" row of `:3822`) already takes the stall to 0.44-0.50 / 0.39-0.42 s for +50 % arrival (3.47-3.51 s against
   2.40-2.85 s). That is why the item says the only lever left is the chunk's *shape*, not its size: slicing should buy
   the clamp's stall **without** the clamp's arrival.
2. The decoders' tokens arrive two ways today: one rides each chunk (their rows join the chunk's GEMMs, nearly free)
   and the rest come from the interleave's decode-only steps between chunks (`prefill-interleave: auto:1` — 33 tok/s
   against 70 idle at two streams). The interleave is what costs the arrival its TTFT: 9.5 / 10.3 s with `auto:1`
   against 5.0 / 5.5 s with it off at 16K, where cold is 4.6 s (3.50K tok/s).

So the stall is `C + D` (one chunk, one decode step, plus the scheduler noise of §10), and the way to divide it without
losing either column of that table is to divide the *trunk*, not the rows.

## 2. The composition

### 2.1 What a sub-step is

A sub-step is a normal step, planned by the normal path, whose batch is

- rows `[0, n_tok_decode)` — the decode set's rows exactly as a decode step would issue them (one row a sequence, §D3)
  — run through **all 42 layers**;
- rows `[n_tok_decode, n_tok)` — the chunk's rows, at their positions `r.n_computed + i` — run through layers
  `[layer_lo, layer_hi)` only.

Per layer the row extent is a runtime value: `rows = in_slice ? n_tok : n_tok_decode`. Every op of the layer loop is
issued over `rows` rows (the arity is already a runtime `int64_t` in every one of them); the ops that take the
`RadBatch` instead of a row count get a **decode view** — a stack copy with `phase = RAD_PHASE_DECODE`,
`n_seq = n_seq_decode`, `n_tok = n_tok_decode`, `n_out = 0` — which is exactly a decode-only pass of the same rows,
and which needs no ABI change because the decode rows are the *first* sequences of `cu_seqlens`/`seq_ids`/`q_lens`.

The invariant the whole design rests on:

> rows `[0, n_tok_decode)` are the current sub-step's, rows `[n_tok_decode, n_tok)` are the chunk's and are frozen
> between sub-steps.

Nothing else about a step changes: the arena level is the same (same `n_tok`), the plan's `select`/`nonabs`/`live` are
the same (same positions, same context), the KV block tables and slot mapping are the same, the stager is armed the same
way, and `plan()` in the plugin computes the same `p.D`/`p.DT`.

### 2.2 The slice boundaries and m

42 layers (`docs/ARCHITECTURES.md:3280`). `L_j = (j · 42) / m`, integer division, so the slices are balanced and
differ by at most one layer. A sub-step is the slice's chunk rows plus the decode set's own pass (§2.7), so it lasts
`C/m + D` and the decoders' gap is that same number:

| m | layers a slice | sub-step = gap | chunk total `C + m·D` | against the unsliced chunk |
|---|---|---|---|---|
| 1 | 42 | 578 ms | 578 ms | — |
| 2 | 21, 21 | 296 ms | 592 ms | +14 ms |
| 3 | 14, 14, 14 | 202 ms | 605 ms | +27 ms |
| 4 | 11, 11, 10, 10 | 155 ms | 619 ms | +41 ms |
| 6 | 7 ×6 | 108 ms | 646 ms | +68 ms |
| 8 | 6, 5, 6, 5, 5, 5, 5, 5 | 84 ms | 673 ms | +95 ms |

(`C = 565 ms`, `D = 13.5 ms`, the model of §2.7.) Nothing requires a slice boundary at a particular layer: a layer is a
self-contained block (attention, junctions, MoE, Engram gate) and the trunk has no cross-layer state that spans a block
except through the residual and the junction's folded input, both of which are per-row and persisted (§3).

m is chosen by the scheduler, not by the token count:

```
C = ema_chunk_s_      (the scheduler already learns it: scheduler.h:903)
D = ema_decode_s_     (likewise)
m = clamp(ceil(C / target), 1, min(8, 1 + floor(cost_pct * C / D)))
```

with `--chunk-slice-target-ms` 150 and `--chunk-slice-cost-pct` 10 by default. At C = 565 ms and D = 13.5 ms that is
`ceil(565/150) = 4`, capped by `1 + floor(0.10 · 565 / 13.5) = 5` ⇒ **m = 4**, cost 41 ms (7.2 % of the chunk), stall
155 ms. The cap is what keeps the item honest at its own promise ("prefill rate and TTFT unchanged"): with the cost
share at 10 % no chunk grows by more than a tenth, and the target decides the rest. A chunk of 256 rows (C ≈ 444 ms)
gets m = 3 (150 + 27 = 177 ms, +6 %); a 1024-row chunk (C ≈ 300 ms) m = 2 (150 + 14 = 164 ms).

### 2.3 Which steps are sliced, and which never

Sliced, in order of the checks:

1. `plan_.phase == RAD_PHASE_MIXED` with `n_seq_decode > 0` and one chunk entry (`P == 1`);
2. that chunk entry's `n_tokens ≥ slice_min_rows`: start at 128 rows and let the lane decide. The floor does not
   transfer from M-03 (which arms the stager only above its top level, 1025 rows at 2048) because a slice is not a step:
   its decode band is staged as well and the chunk's experts are read once across the whole group, not once a slice;
3. `chunk_slices > 0` and the plugin's `RadArchProbe::slice_layers_ok`;
4. the chunk's media rows are scattered by the group's first sub-step only (the step head runs the media scatter when
   `n_mm_rows > 0`, and the engine zeroes it after the step), so no sub-step after the first needs a media row;
5. no row of the decode set rides a verify row (`n_spec == 0`, §D3) — with a speculative depth on, m = 1;
6. m ≥ 2 after the law above.

Never sliced: a prefill-only step (there is no decoder to hand a slice to — except behind the test hook
`--chunk-slices-prefill`, which exists so a single-stream greedy run exercises the machinery, §8); a step carrying
two chunk entries (a spanned step: `--prefill-span` — one chunk group is the unit); a step whose chunk carries an
in-step checkpoint cut (`ckpt_cut > 0`, prefill-only by ABI anyway); a step whose decoders have a draft in flight
(§2.3 rule 5) or whose `n_spec` is not 0; a pass with the pipeline
(`layer_lo > 0 || layer_hi < n_layer` ⇒ serial, and `pipe` is only taken for `n_seq == 1`, so a mixed step never sees
it); a pass with `taps_on()` or a calibration window.

### 2.4 The group

A group is created when the scheduler slices a chunk for the first time and ends at its last sub-step:

```
struct ChunkGroup {
    int32_t slot = -1;      /* the request; -1 = no group */
    int32_t n_tokens = 0;   /* the chunk's rows, fixed */
    int32_t n_slices = 0;   /* m */
    int32_t next = 0;       /* j of the last sub-step built */
    int32_t lo = 0, hi = 0; /* the last sub-step's layer range */
};
```

The frozen decode set needs no field: it is `plan_.e`'s decode prefix, which is the scheduler's running set read again
with nothing entering or leaving it (§D3) and one row a sequence, so the same sequences come back in the same order.

Inside a group:

- the decode rows are planned exactly as a decode step plans them (the same loop, the same `n_spec`, the same draft
  output), from the frozen set — so `n_tok_decode` is the same number in every sub-step, and the chunk's base does not
  move;
- the chunk entry is *carried*, not re-planned: `sched_tokens` stays at the chunk's row count, `plan_chunk` is not
  called again, `busy_cap`/`mixed_target_`/the stager-floor clamp do not touch a group;
- admission is off (`admit_one` is not called), preemption is off, a draft-depth change (`draft_.adaptive()`) is
  deferred, and a finish or a cancel is recorded and acted on at the group's end;
- the issue-ahead path builds the *next slice* of the same group (`step_next_locked` gets a group branch at its top:
  same entries, `next+1`, its layer range) instead of planning a new chunk, so a sub-step still overlaps the host work
  of the next one.

The group ends after the slice with `layer_hi == n_layer`. Then the chunk's commit happens (§2.5), the request becomes
an ordinary decode or finishes, and the next step is planned normally. A group is at most `C + (m-1)·D` ≈ 0.6 s, which
is the same order as the chunk step it replaces, so holding admission and preemption inside it costs no more than a
chunk step does today.

### 2.5 Commits, deferral, and what the step reports

Per sub-step the decode rows commit as they always do (`r.n_computed += accepted rows`, KV window trim, sink progress).
The chunk's row count does **not** advance until the last sub-step. Concretely, in the commit path
(`scheduler.cpp:3400-3470`) the prefill branch is gated on the entry being the group's last slice:

- `r.n_computed += e.n_tokens`, `kv_->trim_window(...)`, `step_prefill_tok_`, `sink_prompt_progress(...)`, the
  "fully placed" block (`sink_prompt_stats`, `last_prefill_ids_`), the prefix publish and `--draft-suffix`'s
  `suffix_index` all happen on the last slice only;
- `e.produces_token` is planned once, as today, from `r.n_computed + s.sched_tokens >= s.seq_len()` (`scheduler.cpp:2675`,
  `:3286`), and is **masked by the last-slice flag**. The mask is not cosmetic: `r.n_computed` does not advance inside
  the group while `sched_tokens` holds the chunk, so that expression is true in every sub-step, and unmasked the chunk
  would emit its token m times. Masked, early sub-steps report "no token from the chunk" — the existing path that
  already covers a mid-prompt chunk, so `n_out` is the decode rows' and the sampler/`last_prefill_ids_` need no new case;
- `n_checkpoints` in the batch is filled on the last slice only, so the engine's `ckpt_stage_arm` is a no-op before it,
  and the stage copy sees the complete chunk.

The entry carries the flag (`StepEntry::slice_last`, or `layer_hi == n_layer` read at commit — the plan has it), so the
commit needs a boolean, not the group.

### 2.6 The interleave and the held chunk

`held_prefill_`/`interleave_left_` exist to *insert* decode-only steps between chunks; a group already carries m-1 extra
decoder tokens that a decode step would have cost D each. So the two are substitutes, not complements:

- with the interleave as it is, the group's decoders gain m-1 tokens a chunk for the group's extra `(m-1)·D` of arrival
  time — the arrival's TTFT grows by the same wall time the interleave would have needed for those tokens;
- with the interleave reduced, the arrival is no longer than today's and the decoders' rate is unchanged.

Both are measured (§10). The design does **not** force either: `prefill-interleave` keeps its own meaning, the group's
chunk is never *held* (a held chunk is a row reservation for the interleave), and `busy-prefill-chunk` still decides
how many rows a chunk gets — including whether a chunk is worth slicing at all (§2.3 rule 2).

### 2.7 The cost model

```
sub-step = decoder gap  ≈ C/m + D    (the slice's chunk rows + the decode set's own pass)
chunk total            ≈ C + m·D
against today          = + (m-1)·D
```

At `C = 565 ms`, `D = 13.5 ms`: sub-step 296 ms at m=2, 202 at m=3, 155 at m=4, 108 at m=6, 84 at m=8 (table in §2.2).
The item's "0.15-0.2 s at m = 4" reproduces at 155 ms; its "0.5-0.8 s" is the in-tree window's 0.58-0.78 s.

Two honest corrections to the item's estimate:

- **The item's 50 MiB is `tr.h` alone.** `tr.h` is 2048 × 4 × 3072 bf16 = 48 MiB (50.3 MB) — the item's parenthetical is
  decimal MB — and the chunk also needs `tr.xn` (12 MiB), `tr.post` (32 KiB) and the boundary junction's code pair (6 MiB
  + 192 KiB) once the fold is kept at the boundary (§3). 66 MiB, not 50.
- **"Prefill rate and TTFT unchanged" holds only if the interleave gives back what the group takes.** The group's chunk
  costs `(m-1)·D` more than the unsliced one, and 3 × 41 ms is 122 ms on the in-tree window's 3-chunk 5.7K arrival
  (2.40-2.85 s, so +4-5 % of TTFT) and 8 × 41 ms is ~325 ms on a 16K arrival (+3.4 % of 9.5 s). The same three (or
  eight) times `(m-1)` decoder tokens are what the interleave no longer has to buy, so the *pair* is flat — but a lane run
  has to show it, and it must be shown as a pair.

## 3. The persistent chunk state

Per sub-step, the chunk's rows stop at a layer boundary and resume there `(m-1)` times, so everything the next layer
needs of those rows must survive the step. At HEAD the trunk's per-row buffers are declared in
`arch/hyv4flash/hyv4flash.cpp:679-689` with `decl_b`'s default `RAD_BUF_TRANSIENT` (`arch/common/rad_arch.h:466`; a
step's arena region, reused by the next step) — and the pipe declaration's own comment at `:1081-1083` says the
connection buffers are "PERSIST already", which they are not. This change is what makes three of them so.

| buffer | shape | bytes at 2048 rows | today | with slicing |
|---|---|---|---|---|
| `tr.h` | T × hc(4) × 3072 bf16 | 48 MiB | TRANSIENT | **PERSIST** |
| `tr.xn` | T × 3072 bf16 | 12 MiB | TRANSIENT | **PERSIST** |
| `tr.post` | T × hc(4) f32 | 32 KiB | TRANSIENT | **PERSIST** |
| `codes.q8` | T × 3072 int8 | 6 MiB | TRANSIENT | **PERSIST** |
| `codes.s8` | T × 24 f32 | 192 KiB | TRANSIENT | **PERSIST** |
| `tr.x` (`hc_x`), `tr.y` (`block_out`), `x0` (`embed`) | T × 3072 bf16 | 12 MiB each | TRANSIENT | unchanged |
| `final_hidden` | T × 3072 bf16 | 12 MiB | PERSIST | unchanged |
| `dfly.sel_snap.<l>` / `nsel_snap.<l>` | T × G i32 | per layer | PERSIST | unchanged |
| Engram history / conv state | per sequence | — | PERSIST (KV state slot) | unchanged |

**66 MiB a rank** (69.4 MB), charged to the arena's *fixed* region — the bring-up line
`activation arena: … use … of … (the fixed region is …)` grows by it, and the same bytes come off the KV pool and the
expert slab through `core/mem/`'s budget. Only declared when the feature can be on (`RadBuildCtx::layer_slices`
carries the flag — the house pattern, like `span_pass_step` — and `RadArchProbe::slice_layers_ok` reports it), so a
server with `--chunk-slices off` keeps today's graph, today's fixed
region and today's tape keys bit for bit.

Why these five and not more:

- `tr.h` is the residual (hc-multiplied hidden state); `tr.post` is the connection term the current block's junction
  wrote for the *next* block's add-back (`hyv4flash_common.h`, the junction writes `h`, `post` and `xn`);
- `tr.xn` is the *input norm* of the current block. It is persisted rather than recomputed because the fused
  `rmsnorm_ihc_junction` that produces it is a different kernel from the `op_attn_norm` that would recompute it, and
  "probably the same bits" is not a claim this item may make. If a build-card test shows they are bit-identical, `tr.xn`
  drops out of the set (−12 MiB); the design keeps it until that test exists.
- the int8 **code pair** of the boundary junction is the junction's own output (`codes.g8 = 128`, rotated int8 with
  per-128 f32 scales, `hyv4flash_common.h:232-253`): the fold at a slice boundary means the *previous* slice's last
  junction left the next block's input *quantised*, and the next slice's first layer reads that pair. So it persists for
  the same reason `xn` does — the fold is kept, not redone. `Codes::get` declares a pair per width K and per role tag,
  so the persistent set is "every pair a junction writes and a later block reads": at this model's trunk that is the
  E-wide (3072) pair, 6 MiB + 192 KiB, and S-02b must enumerate them from the declared graph rather than assume one —
  a boundary that lands where a role-tagged or narrower pair is fed must persist that pair too.
- `tr.x`/`tr.y`/`x0` are written and read inside one layer (or the step head): `hc_attn.pre` and `hc_ffn.pre`
  *write* `tr.x` from `tr.h`/`tr.post`, `attn.core`/the junctions write `tr.y`, and `x0` is the head's embed output
  that `op_stream` copies into `tr.h`'s streams. Nothing reads any of them at a boundary, which is why they stay
  transient. (If a lane run disagrees, the fix is to add the buffer to the set, never to reorder the layers.)
- `final_hidden` and the DFly2 snapshots are already `RAD_BUF_PERSIST` (`hyv4flash_dfly.h`) — the query pass reads them
  after the trunk has finished, which is now the last sub-step, so they needed nothing.

Alternatives rejected, and why:

- **Re-base instead of persist**: keep the chunk's rows at the *front* of the arena and copy them into a private buffer
  at each boundary. That is 66 MiB of copies a boundary (≈ 20 µs at 3 TB/s, so affordable) but it needs a second 66 MiB
  region (132 MiB), a copy op, and it makes the row band move between sub-steps — every op's row offsets would change
  per sub-step, which multiplies the shape space the recorder, the stager and the taps reason about. Persisting is
  smaller and narrower.
- **Chunk rows first, decode rows after**: the chunk's base would be 0 and the decode set free to change — but the
  decode-rows-first order is the batch contract (`core/sched/batch.h`, `n_seq_decode`, `batch_split`), the attention
  split and every plugin's row arithmetic depend on it, and inverting it for all arches is a far bigger change than
  freezing m sub-steps' worth of admission.
- **A fixed decode band** (rows `[0, 64)` for decode, chunk from row 64): also decouples the base, but the invalid rows
  would need masking in every row-batched op (and their KV writes suppressing), which is a kernel-level change in
  exchange for the admission freedom we do not need.
- **Recompute `xn`/codes at the boundary instead of the fold**: changes kernel shapes and therefore possibly bits (§8),
  and would need the *decode* rows to take the `entered = false` path in a layer where the chunk rows take
  `entered = true` — two paths for one layer in one sub-step.

The taps and calibration: a tap buffer (`m.t_*.step`, `RADIANCE_HY4_TAPS`) is a per-layer copy of a whole-trunk value; a
sliced pass fills the chunk rows' taps only for the slice's layers, so a tap read after a sliced chunk would be stale.
The plugin therefore reports `slice_layers_ok = 0` with taps on or with a calibration window declared
(`ctx->calib_layer_lo/hi`), and the scheduler plans m = 1.

## 5. The stager, per slice

The stager already stages *per layer of the pass*: `begin_pass` arms when `b->n_tok >= min_rows_`, and each layer is
staged when its `first_op` is reached in op order, so a sliced pass stages exactly the slice's layers for the chunk's
rows (plus, outside the slice, the decode rows' own experts, which the same per-layer staging discovers from the route
report with `rows` rows). That is the behaviour the item asks for, and it needs one change:

- **the early staging of the next pass needs a layer base.** `n_early_`/`first_of_` prefetch the *next* trunk pass's
  first layers while this one runs, and `set_next_prefill(bool more)` (`core/engine.cpp:2485-2495`) tells it only that
  another prefill follows. Inside a group the next pass starts at `L_{j+1}`, not at layer 0, so the signature becomes
  `set_next_prefill(bool more, int32_t first_layer)` and the engine passes the *next* plan's `layer_lo` (0 for an
  unsliced pass, which is every pass written today).

Two invariants that hold and must be asserted, not assumed:

- the arena level is unchanged inside a group (`n_tok` is the same), so the stager's ring is not rebased and no slot
  moves between sub-steps;
- **the copy is paid once a group, not once a slice — and that is the design's main assumption.** A sub-step is a pass
  with `n_tok = T`, so it arms the stager exactly as the unsliced chunk would; but the chunk's rows are the *same rows*
  at every slice, so their routing is the same expert set, and the second slice's staging finds it in the ring the way
  M-03b's fourth consecutive 1984-row chunk found it (`notes/backlog/closed/M-03b.md:89-95`: `stage_layers` 123, its
  copy cheap). The number that decides this is the ring's capacity against the group's *union*: at 1728-1984 rows a
  layer routes almost the whole pooled set, so if the ring cannot hold ~m × 42 layer-sets, the early layers are evicted
  and re-copied — ~90 ms a copy at the 3.7-4 GiB a rank and ~40 GB/s that M-03b measured, i.e. up to m × 90 ms against a
  155 ms slice. §10's first measurement is therefore `stage_layers`/`staged_bytes` and the copy's share of a sub-step,
  before any stall number is believed; if the ring cannot hold the group's union, the options are M-03b's own (copy only
  what is not resident, paced over the layers before the slice) and, failing that, not slicing a chunk whose routing
  overflows the ring. The decode band's own experts are staged at the out-of-slice layers on every sub-step, but that
  band is `p.DT` rows of one to four sequences (a few experts), and it is inside `D` already.

## 6. Checkpoints, prefix cache, cancellation

- **A chunk that ends on a checkpoint** (`plan_chunk` cuts the chunk *at* the checkpoint, so `ckpt_tok + 1 == n_tokens`)
  is sliced, and the snapshot is staged after the last sub-step: the engine's `ckpt_stage_arm` reads the batch's
  `n_checkpoints`, which the builder fills on the last slice only. Nothing in the snapshot path changes, and the KV
  bytes it copies are the chunk's own, written by the last slice.
- **A snapshot strictly inside a chunk** (`ckpt_tok + 1 < n_tokens`) — only possible for a plugin with an in-step
  snapshot (`RadArchProbe::ckpt_snap_ok`/`RadBatch::ckpt_cut`), which hy4-flash is not (only `qwen4exp_fp8` reports it)
  — makes the chunk m = 1. The guard is one line and it keeps the design honest for the next arch.
- **The prefix cache** is published from `r.n_computed` and the KV's own bookkeeping; both wait for the last slice, so
  no lookup can see a half-layered chunk.
- **A finish, a cancel or a preemption** inside a group is deferred to the group's end (§D3/D12): the row is still
  issued, the results are dropped at commit exactly as they are dropped today for a request that left `Running`.

## 7. The plugin's step

`arch/hyv4flash/hyv4flash.cpp:1195-1401`, `StepPlan plan()` unchanged. The step gains a slice and a row extent:

```c
    const int64_t lo = batch->layer_lo, hi = batch->layer_hi ? batch->layer_hi : s.n_layer;
    /* The decode rows' view: the batch is the first n_seq_decode sequences, which is exactly a
     * decode-only pass over the same rows. */
    RadBatch dec = *batch;
    if (lo > 0 || hi < s.n_layer) {
        dec.phase = RAD_PHASE_DECODE; dec.n_seq = p.D; dec.n_tok = p.DT; dec.n_out = 0;
    }
    const RadBatch* bd = (lo == 0 && hi == s.n_layer) ? batch : &dec;
```

and the step's row extent, per op:

- the step-head ops (`embed`, the media scatter and its all-reduce, and `op_stream` copying `x0` into `tr.h`'s hc
  streams) run over the first `lo == 0 ? T : p.DT` rows — never over the chunk's rows twice, and always from row 0, so a
  head run over `p.DT` rows touches the decode band only and leaves the chunk band of `tr.h` as it persisted it;
- the media scatter runs on the group's first sub-step only (the engine zeroes `n_mm_rows` after it);
- in the layer loop, `rows = (i >= lo && i < hi) ? T : p.DT`, and every per-layer op is issued over `rows`: the
  junctions, the norms, `attn.front`/`ix.step`/`attn.core` (with `bd`), the `df.snap_step` snapshots, the FFN/MoE
  (`l.ffn.step(c, bd, je)`), the Engram step (`l.engrams[...].step(c, bd)`), the calib taps (off by D11);
- `entered` at the slice's start is `i == lo && lo > 0 ? (layers[lo-1].j_end && layers[lo-1].j_end.tail) : false`,
  which is the same boolean the previous slice ended with — so the chain neither restarts nor double-folds at the
  boundary. It is correct for both row bands because each band's layer chain is contiguous and every layer's tail writes
  the rows it read: the chunk rows' band was left by the previous slice's last layer, the decode rows' band by the layer
  `lo-1` of *this* sub-step, over `p.DT` rows;
- the loop ends at `hi`. `hi == s.n_layer` is the "the whole trunk ran" test that today is `!entered` after the loop (the
  head's guard, `m.hc_head.pre`/`op_norm`), and the head/gather/sample still run over `T` rows for the norm and
  `batch->n_out` rows for the gather, exactly as today, so the chunk's logits are bit-identical (§8);
- the pipeline is refused (§D11); `pipe_rows`/`n0`/`n1` are only computed for `n_seq == 1` anyway.

What must *not* change: the per-layer op sequence. A sliced pass issues, for the chunk rows, the same ops in the same
order with the same launch shapes as the unsliced pass (each layer once, `M = T`), which is the whole reason the
continuation can be byte-identical. The only row count that differs is the *decode* band's outside the slice.

## 8. Byte-identical continuation: what is claimed, and how it is tested

Claimed (and the tests must show it):

| what | against | why it must be identical |
|---|---|---|
| the chunk's KV bytes, every layer | the unsliced chunk | same rows, same positions, same per-layer op sequence, same `M = T`, same block table, same store kernel |
| the chunk's `final_hidden` row and logits | the unsliced chunk | the head runs on the same rows with the same `M = T` |
| the prompt's first token, and the greedy continuation from it | the unsliced run | the first token is drawn from those logits; the continuation is then a decode of a KV that is the same bytes |
| TTFT of a lone (unmixed) prefill | today | a lone prefill is never sliced (§2.3) |

Not claimed: a *decoder's* token inside a sliced mixed step. Its non-slice layers run with `M = n_tok_decode` instead of
`M = n_tok` — the row count of a GEMM changes the kernel's tiling band, and this tree's own text says the trunk's GEMMs
are batch-dependent (`docs/ARCHITECTURES.md:3863`). That is the same caveat the drafter's multi-stream losslessness
already carries, and it is *not* a lossy lever: no accumulation type, rounding step, quantisation or approximation
changes — only which rows share a launch. This tree states the same boundary for a change of chunk size: "a long prompt's
answer can differ the way it does between any two chunk sizes … with a prompt that is one chunk either way bit-identical; no
dtype, kernel or accumulation changes" (`docs/ARCHITECTURES.md:3852-3854`). S-02 is stronger on the prompt than that:
the chunk's *rows* keep their op sequence and their `M`, so the prompt is identical for any prompt length. It must be
stated in the item's Verify row (the design's D9), because a lane run comparing two greedy runs *with decoders riding*
will see the decoders' text differ and could read it as a bug.

Tests:

1. **in-tree, no card** — `tests/sched_test.cpp`: a mixed step sliced into m has `m` steps' plans, one chunk entry each,
   `layer_lo/hi` = the boundaries of §2.2, `n_tok_decode` constant across the group, `n_tok` constant, the chunk's
   commit only on the last slice (`r.n_computed` unchanged on the others), `produces_token` false before it, and the
   group's end restoring ordinary planning. Plus the refusals: two chunk entries, `n_mm_rows > 0` after the first slice,
   taps on, `slice_layers_ok = 0`, m = 1.
2. **in-tree, one card** — `--chunk-slices-prefill m` slices a *prefill-only* step too, so a single-stream greedy run of
   a long prompt is served by sliced passes and the same run is served by m = 1 for the A/B. The test: the same prompt
   served both ways gives the same text, and a per-layer dump of the chunk's KV bytes and the `final_hidden` row (a
   checksum the engine can print behind a flag, or a `rad-*` tool) compares equal. This is the test that exercises the
   persistent set, the boundary fold, the head and the stager in one run without needing a mixed load.
3. **lane** — `probe.py greedy` (`scripts/backlog/probe.py`, `phase: greedy`, sha256 of the text) before and after, on
   the same lane and the same config; the chunk rows must match. With decoders riding, the *prompt's* first token must
   match; the decoders' text is not compared (D9).

## 11. Risks, and what would close the item

- **The staging could dominate.** §5's assumption is that the chunk's rows route the same experts at every slice, so
  the copy is paid once and the later slices find the ring warm. If the ring cannot hold the group's union, the early
  layers are evicted and re-copied: ~90 ms a copy (3.7-4 GiB a rank at ~40 GB/s, M-03b) against a 155 ms slice at
  m = 4, which would erase the gain. That is why §10 measures `stage_layers` and the copy share first, and why the
  fallbacks live in §5 rather than in a follow-up. Note also that a sliced step still reads each layer's experts once,
  so the item's premise ("each layer's experts read once per 2048 rows") stays true — it is the *copy* into the ring
  that must not multiply.
- **The boundary cost.** Each slice boundary re-reads `xn`/codes for 2048 rows (12 MiB + 6 MiB) from the arena, and
  re-launches 42/… layers' first ops: ~6 µs of traffic a boundary at 3 TB/s, i.e. nothing against 155 ms. If it is not
  nothing, the model's D is wrong, not the design.
- **The frozen decode set** is the sharpest edge: any admission, preemption, finish or cancel inside a group is a bug
  that shows as a wrong token at the chunk's base. It is why this is an L: the tests must cover each of those four
  events mid-group. Speculation is refused inside a group rather than frozen (§D3), so a recipe with
  `--num-speculative-tokens` above 0 gets no slicing until the draft passes are group steps too.
- **Arena and KV budget**: +66 MiB a rank at 2048 rows, and the levels at smaller `max_tok` need their own declares (the
  plugin already declares again per level in `probe_arena_levels`). If a level's fixed region pushes the KV pool below
  the prefix-cache budget, the flag stays off in that recipe — that is a policy decision for the lane run, not a
  correctness one.
- **The claim's edges** (D9): a decoder's token differs across batch shapes; if a lane run compares the full text of a
  mixed load it will see that and it is not a regression.
- **What would close the item without merging**: the stall not falling below ~0.35 s at m ≤ 4, or the rate falling
  outside noise with the pair flat, or the persistent set costing more than the item's budget in KV (measured in the
  bring-up line). Then `closed/S-02.md` with the numbers, and FP-10 stays research.
